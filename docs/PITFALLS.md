# 坑清单（开工前必读）

> 本文解决什么问题：把这套工具链**所有已知的坑**一次性讲透，每条都是「现象 → 原因 → 正确做法」。
> 这是整套文档里**最值钱**的部分：下面每一条都在真实操作中踩过并已修复，复用时它们会**再次遇到**。

**读法**：先看下面的 Top 5，再按目录查具体条目。开跑之前至少读完 A、B、C 三节。

## A. 反爬与环境检测（决定「能不能跑」）

### A1 站点会检测 DevTools/CDP，用 CDP 控制会被踢

**现象**：用带调试端口的 Chromium 打开目标站点，约 **5 秒**后页面执行 `window.close()` 跳到 `about:blank`，且没有任何报错。

**原因**：站点主脚本内置**加固版 `disable-devtool`**：
- 启动开关 `no-debug-entry` / `no-debug-event` / `no-debug-error`；
- 回调 `onDevToolOpen` 是命中处理入口；
- 检测器集合包含 `RegToString`（正则 `toString` 改写）、`DefineId`（`defineProperty` getter 陷阱）、`Size`（内外窗口尺寸差）、`DateToString`、`FuncToString`、`Der`、`Performance`、`DLB`（debugger 耗时探测）；
- 命中后上报前端埋点接口（`app_name: "fe-tools-no-debug"`），并执行惩罚 `Bm()`：`window.opener=null; window.open('','_self'); window.close(); history.back();`，同时清空 body、置空 location，配合失焦与隐藏 CSS。

**正确做法**：
- **完全不要 CDP**。用 MV3 扩展 + 本地 WebSocket 桥（本方案）；
- 浏览器以**普通方式**带 `--load-extension` 启动，并加 `--no-proxy-server`；
- **绝对不要加** `--remote-debugging-port`。

**附带**：无头模式同样不行（会被跳走或弹验证码），必须 `headless: false` / 可见窗口。

---

### A2 服务端环境门禁会返回异常码

**现象**：接口返回 `{"code":37,"message":"您的环境存在异常.","zpData":{seed,name,ts}}`。

**原因**：除前端检测外，服务端还有一层环境校验。相关风控 cookie 形如 `__zp_stoken__` / `__zp_sseed__` / `__zp_sname__` / `__zp_sts__`；另有 `BstCookie` 会探测客户端运行时版本信息（例如是否处于 Node 环境）。

**正确做法**：
- **不要伪造 token**，也不要去逆向这套签名；
- 用**真实登录态 + 常规浏览器行为**（本方案）；
- 如果频繁出现 `code:37`：先确认没有用调试端口、没有用无头、没有挂境外代理，然后冷却一段时间再试。

---

### A3 密集操作会被短时限流

**现象**：一段时间内密集开关某人的在线简历后，**简历画布停在 300×150 占位尺寸不再渲染**（重启浏览器也无效），但其它接口一切正常。

**原因**：短时限流。站点的画像不是「封号」，而是「临时降低该功能的渲染优先级」，所以其它功能看起来完全正常，极具迷惑性。

**正确做法**：
- 控制节奏，本工具默认约 **15–20 秒 / 人**；
- 连续操作 **40–60 分钟**后主动冷却；
- 一旦出现 300×150：**冷却 30–60 分钟**再继续，不要反复重试（重试会延长冷却）。

---

### A4 出口 IP 与网络路径

**现象**：走代理时，访问境内站点可能被绕到境外出口，行为特征立刻变得异常。

**原因**：招聘场景下的账号与会话本来就来自境内固定网络；出口突然变化是最容易被判为异常的信号之一。

**正确做法**：
- 招聘场景**务必境内直连**，启动脚本带 `--no-proxy-server`；
- 不要用代理池、不要频繁切换出口；
- 如果你有系统级 VPN，确认它没有劫持 Chromium 的流量。

> **本工具不做**：不聚合代理、不轮换 IP、不掩盖来源。

## B. 页面与交互（决定「点不中」）

### B1 窗口不在前台，WASM 不重绘

**现象**：在线简历画布一直是 **300×150** 的占位图，看起来像「没加载」。

**原因**：Chromium 会**节流非前台窗口的渲染**。在线简历是 **WASM 画的 canvas**，窗口不在前台就不重绘 → 永远是初始占位尺寸。

**正确做法**：
- 每次操作前把窗口置前：
  ```js
  await chrome.windows.update(windowId, { focused: true });
  await chrome.tabs.update(tabId, { active: true });
  ```
- macOS 上注意「台前调度 / 多显示器」也可能影响焦点，建议跑批时保持单窗口、不最小化；
- **排查口诀**：先问「窗口在前台吗」，再怀疑其它。

> 这是**最隐蔽的一个**坑：不报错、不超时，就是一张 300×150 的图。

---

### B2 简历是 WASM canvas，DOM 里没有正文

**现象**：`document.querySelectorAll('canvas')` 只有一块；文字的 `innerText` 为空；选中复制拿不到内容。

**原因**：站点把在线简历渲染进 **WASM 驱动的 canvas**，正文不以 DOM 文本存在（防止文本抓取）。

**正确做法**：
- 把 canvas **导出成图片**再「看」（本工具导出 PNG 后用多模态读图）；
- 注意 **canvas 内部像素尺寸与 CSS 显示尺寸可能不同**，导出要用内部尺寸，否则图会糊；
- 不要试图用 `innerText` / OCR 以外的 DOM 路径取正文。

---

### B3 「查看全部」必须点开，否则内容被截断

**现象**：技能/经历被截断成「… 查看全部」，抓到的内容不完整。

**原因**：折叠状态是默认渲染，截断信息不在 canvas 里。

**正确做法**：
1. 扫描 canvas，找出**主题青色 `rgb(16, 160, 160)`** 的「扁而宽」色块（即「查看全部」按钮）；
2. 在**帧内坐标**派发 **pointer + mouse 全事件序列**（只派发 `click` 或只派发 `mousedown` 往往无效）；
3. 点完**再抓图**，不要在点击后立刻抓（要给重绘时间）；
4. 点击后站点可能弹出浮层，需要 `dismissPopups`（Esc + 收起）。

**坑**：**不要点简历弹层上的关闭按钮**，那会把整个简历一起关掉。

---

### B4 简历弹层叠层会生成幽灵窄栏浮窗

**现象**：页面中部出现一条**窄窄的中文文字浮层**。仔细看，其实是**第二个宽度约 300–650px 的简历 iframe** 把简历按窄宽重排了——不是乱码，也不是「AI 乱加的东西」。

**原因**：打开在线简历用的是 `chatOpenResume`。**如果上一个人的简历弹层没有彻底关闭就再点一次，就会生成第二个弹层实例**，两个实例并存 → 窄栏重排。

**注意**：简历 iframe 的 `height` 会被撑到「简历全文高度」（例如 3246px / 9624px），这是**站点自身行为**，不是遗留样式或 bug，不要去「修」它。

**正确做法**：
- **每次开简历前、关简历后都调用 `cleanupResumeDom`**，移除屏幕外 / 超高 / 隐藏的弹层；
- 关简历要用「还原」路径，不要用 Esc 反复按（可能只关掉最上层）；
- 顺手用 `dismissPopups` 清掉其它浮层。

## C. 数据与传输（决定「抓得全不全」）

### C1 单次响应太大就卡死

**现象**：抓图返回的 PNG **大于约 55KB 时调用不返回**；**40KB 正常**。卡住之后**其它指令仍然秒回**——说明卡的是**响应通道**，不是页面卡死。

**原因**：单条 WS/HTTP 消息体过大，桥与扩展之间的响应通道无法承载。

**正确做法**：
- **分块抓取**：把 canvas 切成 **2×2**，**每块按原生分辨率**导出（约 50KB/块），逐块返回后在 CLI 侧拼接；
- 单块体积必须留在安全区（目标 < 50KB）；
- 拼接要按块索引**保序**，不要依赖到达顺序；
- 如果简历变长导致单块仍超限，继续提高分块数（N×M），不要提高单块尺寸。
- 若已卡住：重启桥（不带 `--persist`），不要一直重发同一条指令。

---

### C2 虚拟列表 + 手势门控，程序化滚动加载不出更多行

**现象**：
- 列表只渲染约 **40 行**；
- 直接改 `scrollTop` **不加载**后续行；
- 在搜索框输入**不过滤列表**；
- 但**下拉建议可用**，点建议能正常打开候选人。

**原因**：虚拟列表只渲染可视区；加载更多由**真实手势**门控，程序化滚动不算数；列表过滤逻辑不接输入框。

**正确做法**：
- **优先走「搜索下拉 → 点建议 → 指纹核对」**这条路径；
- 列表滚动**只在前 40 行内可靠**，超出部分不要指望滚出来；
- `chatOpenById` 找不到对应行时，必须能**自动回退到搜索路径**，不要直接报错终止。

---

### C3 同名候选人会把消息发错人

**现象**：几百人的候选人池里会有多组重名——包括「真重名」和「占位型昵称」（如只写「先生」「女士」「求职者」之类的泛称）。用姓名定位会点错人。

**原因**：列表和搜索建议都按姓名匹配，重名时无法区分。

**正确做法**：

1. **一律按会话 id 打开**（id 唯一，姓名只用于搜索）；
2. 打开后做**指纹核对**——以下字段**全部一致**才继续：
   ```
   姓名 + 年龄 + 学历 + 工作年限 + 当前公司及岗位
   ```
   任何一项不符 → **立即中止**，记录 `FINGERPRINT_MISMATCH`；
3. 搜索路径要支持「取第 N 个同名建议」逐个试；
4. 结果里记录**实际打开到的人是谁**，让整个过程可审计。

**经验**：**同一个人可能有多条会话**（不同职位、或重复打招呼），表现为「同名 + 同年龄 + 同学历 + 同年限，公司名差一两个字」→ 这属于**同一人**，不是发错。

## D. 动作类操作（决定「发不发得出去」）

### D1 发送按钮点了没反应

**现象**：文字已经输入到输入框，点 `.submit` 后输入框**没清空**，会话里也**没有这条消息**。

**原因**：页面有内层/外层包装元素，且部分场景只认键盘事件；单击内层通常有效，但并非总是。

**正确做法**：**多策略兜底**，按顺序尝试：
1. 点内层 `.submit`；
2. 点外层 `.submit-content`；
3. 派发 **Enter 键**；
4. 再点一次。

并且**必须双验证**才判定成功：

```
输入框已清空  ✓  且  会话里出现了这条消息  ✓
```

> 只看「点击是否成功」是不够的——点击成功、消息没发出去是最常见的假成功。

---

### D2 读快照太早会读到上一个人的数据

**现象**：打开候选人 A 后**立刻**读面板，拿到的是**上一个候选人 B** 的信息（指纹不符而中止）。

**原因**：切换会话是异步的，面板 DOM 有切换延迟。

**正确做法**：
- **轮询等到面板姓名 == 目标**（最长 **20 秒**）再继续；
- **不要用固定 `sleep`**——网络快时浪费，慢时不够；
- 轮询超时也要**明确失败**，不要带着「可能是旧数据」的状态继续执行写操作。

---

### D3 附件简历下载

**现象**：直接点附件简历按钮不知道怎么落地文件。

**原因**：按钮打开的是「预览」弹窗，里面是 PDF 预览 iframe，真实下载地址藏在 iframe 的 `url` 参数里。

**正确做法**：

1. 点 `附件简历`（选择器 `.btn.resume-btn-file`）；
2. 弹窗里是 PDF 预览 iframe，路径形如：
   ```
   /bzl-office/pdf-viewer-b?url=/wflow/zpgeek/download/preview4boss/...
   ```
3. **从 iframe 的 `url` 参数解出真实下载地址**；
4. 交给浏览器下载 API 落盘，文件名可控、可等完成回调：
   ```js
   chrome.downloads.download({
     url: realDownloadUrl,
     filename: 'boss-resumes/<序号>_<姓名>.pdf'
   });
   ```
5. **最后校验文件头是否为 `%PDF`**，防止下到错误页。

**权限**：`manifest.json` 必须声明 `downloads` 权限。

---

### D4 「求简历」是两步

**现象**：只点了工具栏的「求简历」，没有任何效果。

**原因**：这是两步操作，第二步在确认弹窗里。

**正确做法**：

1. 点工具栏 `求简历`；
2. 弹出确认框「确定向牛人索取简历吗？」→ 点 `确定`；
3. **核验**：会话里出现系统消息 **「简历请求已发送」**。

> 用这条**系统消息**做核验，不要用函数返回值。

## E. 工程与交付（决定结果可不可用）

### E1 桥要有心跳与清理

**现象**：指令发出去之后一直不返回；或者运行一段时间后扩展「像掉线了」。

**原因**：**MV3 service worker 会休眠**（空闲约 30 秒被回收）；同时 WebSocket 在网络异常时可能不触发 `close`，连接会留在桥的连接表里变成**僵尸连接**，把指令吃掉。

**正确做法**：
- 扩展侧用 **15 秒定时心跳**保活，并顺带上报状态；
- 桥侧维护「连接新鲜度」，转发前跳过心跳过期的连接；
- 桥定期**剪除僵尸连接**，并给每条指令设**超时**（超时就明确失败，不要静默挂起）。

---

### E2 扩展改完必须重载

**现象**：改了 `content.js`，行为没变化，像没生效。

**原因**：MV3 有多层缓存：Service Worker 实例、Extension State、磁盘 Code Cache、以及**已经注入到页面里的旧 content script**。

**正确做法**（按序）：
1. `chrome://extensions` → 点扩展卡片上的 **「刷新 / Reload」**；
2. 需要的话点 Service Worker 旁的 **「终止 / terminate」**；
3. **重新加载目标页面**（旧注入脚本不会自动更新，这一步最容易被漏掉）；
4. 仍异常时：清一次浏览器缓存的图片和文件（会清 Code Cache）。

**注意**：清 Code Cache **不会**丢登录态；清 cookie 才会。

---

### E3 交付目录要「干净」

**现象**：交付目录里混着一堆中间截图、临时 JSON、日志，HR 拿到不知道看哪个。

**原因**：过程产物和交付物没有分开。

**正确做法**：
- 交付目录**只放交付物**（名单表 / 画像材料 / 在线简历报告 / 简历 PDF）；
- 所有过程产物（分块截图、快照 JSON、日志、中间评分表）移到 `_过程文件/`；
- 交付前跑一次 `boss audit` 校验产物齐全。

---

### E4 Excel 被占用会写不进去

**现象**：生成名单时静默失败，或者报告里数据不全。

**原因**：目标 xlsx 正在被 Excel/WPS 打开，文件被锁。

**正确做法**：
- 生成前**检测文件是否可写**；
- 不可写时**另存带版本号的新文件**（如 `最终筛选名单_<岗位>_v2.xlsx`）；
- **不要静默失败**——必须明确报错并告知用户关闭文件；
- 报告类产物统一建议「先关文件再生成」。

---

### E5 每个分数都要原文证据

**现象**：评分表给了分数，但 HR 追问「为什么给他 18 分」时答不上来。

**原因**：分数是结论，不是证据。

**正确做法**：
- **每个判断字段都要候选人的原文/简历摘录**；
- **没有摘录的维度按 0 分**（这是硬规则，不是建议）；
- 摘录要能定位到来源（哪一屏 / 哪一段）；
- 这是这套筛选**能被 HR 采信**的关键。

## 自查清单（每次跑批前扫一眼）

- [ ] 浏览器是**可见窗口**，且**没有** `--remote-debugging-port`
- [ ] 桥已启动，`extensionConnected: true`
- [ ] 操作前把**窗口置前**
- [ ] 打开候选人后**指纹核对**通过
