# 架构说明

> 本文解决什么问题：解释**为什么这套工具是「扩展 + 桥」而不是 Playwright/CDP**，以及四层结构各自负责什么、数据怎么流、哪些地方必须小心。

---

## 1. 结论先行

| 方案 | 能否在这里跑通 | 原因 |
| --- | --- | --- |
| Playwright / Puppeteer（CDP） | ❌ 不能 | 站点检测 DevTools/CDP，命中后主动关闭页面并上报 |
| 无头浏览器（headless） | ❌ 不能 | 会被跳转走或弹验证码 |
| 纯 HTTP 请求重放（requests/axios） | ❌ 不能 | 存在服务端环境门禁与签名参数；且在线简历是前端 WASM 渲染的 canvas，没有可直接 GET 的正文接口 |
| **MV3 扩展 + 本地桥（本方案）** | ✅ 可行 | 跑在**真实可见浏览器**里，走**真实登录态**，操作方式是**页面内真实 DOM 事件** |

所以本项目的核心设计目标是：**在真实浏览器的真实页面里，以接近真人的方式，做你本来就要手动做的操作。**

---

## 2. 站点侧的反自动化机制（可观察行为）

> 以下内容来自对公开页面行为的观察，用途是**让工具避免被误判为自动化环境**，不构成任何绕过安全机制的方案。本项目**不**伪造或破解任何风控 token。

### 2.1 前端：加固版 disable-devtool

页面主脚本里集成了一个**加固过的** `disable-devtool` 类模块。它的典型构成：

| 组成 | 作用 |
| --- | --- |
| 启动开关 | `no-debug-entry` / `no-debug-event` / `no-debug-error`，可分别关闭不同检测通道 |
| 回调 | `onDevToolOpen` —— 命中后的处理入口 |
| 检测器集合 | `RegToString`（正则 `toString` 改写检测）、`DefineId`（`Object.defineProperty` 的 getter 陷阱）、`Size`（内外窗口尺寸差）、`DateToString`、`FuncToString`、`Der`（DevTools 检测探针）、`Performance`（时间差探测）、`DLB`（debugger 耗时探测） |

这些检测器的共同特征是：**它们检测的是「调试器存在」这一环境事实**，而不是你的鼠标轨迹。因此：

- **一旦你用 CDP 打开页面**，多个检测器会同时命中；
- 命中后不是弹个警告，而是执行**惩罚**。

### 2.2 惩罚行为 `Bm()`

命中后执行的处理逻辑（可观察到的效果）：

```js
// 等价语义（示意，非原文）
window.opener = null;
window.open('', '_self');   // 清空当前文档
window.close();             // 尝试关闭标签页
history.back();             // 兜底后退
// 同时：清空 document.body、置空 location、配合失焦与隐藏 CSS
```

**实际观感**：页面打开约 **5 秒**后突然变白，地址栏跳到 `about:blank` 或上一个页面，**没有任何报错**。这正是很多人「明明代码没报错，页面自己没了」的原因。

同时会上报一次事件到站点的前端埋点接口（`app_name: "fe-tools-no-debug"`）。

### 2.3 服务端：环境门禁返回异常码

即使前端没被关掉，服务端还有一层环境校验。命中时接口返回：

```json
{ "code": 37, "message": "您的环境存在异常.", "zpData": { "seed": "...", "name": "...", "ts": 0 } }
```

相关的风控 cookie 形如 `__zp_stoken__` / `__zp_sseed__` / `__zp_sname__` / `__zp_sts__`，另有 `BstCookie` 会探测客户端运行时版本信息（例如判断是否处于 Node 环境）。

**本项目的做法**：不伪造、不逆向这些 token，而是**用真实登录态 + 常规浏览器行为**，让这些校验自然通过。

### 2.4 无头模式

`--headless` 下会命中「不像真实用户」的判定：要么被直接跳转，要么弹验证码。**必须使用可见窗口。**

### 2.5 短时限流

密集开关同一批人的在线简历后，会出现**在线简历画布停在 300×150 占位尺寸不再渲染**（重启浏览器也无效），但其它接口一切正常。这是**短时限流**的表现。

**应对**：控制节奏（15–20 秒 / 人），触发后冷却 **30–60 分钟**。详见 [OPERATIONS.md](OPERATIONS.md#4-节奏控制)。

### 2.6 页面交互层面的非自动化设计

| 现象 | 设计意图 | 本项目的应对 |
| --- | --- | --- |
| 在线简历是 **WASM 画的 canvas**，DOM 里没有正文 | 防止文本抓取 | 把 canvas 导出成图片，用多模态读图 |
| 列表是**虚拟列表 + 手势门控**，程序化改 `scrollTop` 不加载更多 | 防止批量拉取 | 优先走「搜索下拉 → 点建议」，滚动只在前 40 行内可靠 |
| 非前台窗口的渲染被节流 | 浏览器自身行为 | 每次操作前把窗口置前 |

## 3. 四层架构

```
┌─ 第 1 层：调用层 ──────────────────────────────────────────────┐
│  boss CLI (packages/cli)        MCP server (packages/mcp-server)│
│  boss list / send / ...         mcp__boss__* 工具               │
└────────────────────────┬───────────────────────────────────────┘
                         │  统一的 JSON 指令信封
┌─ 第 2 层：桥 ──────────▼───────────────────────────────────────┐
│  packages/bridge                                               │
│  HTTP  127.0.0.1:8898   指令入口、/status、/cmd、/scrape              │
│  WS    127.0.0.1:8899   扩展信令通道                            │
│  职责：指令路由 / 请求-响应配对 / 超时 / 僵尸连接清理 / 日志     │
└────────────────────────┬───────────────────────────────────────┘
                         │  WebSocket（扩展主动连入）
┌─ 第 3 层：扩展 ────────▼───────────────────────────────────────┐
│  packages/bridge/extension (MV3)                              │
│  service worker  ── 15s getPlatformInfo 心跳，保活 + 上报状态   │
│  content script  ── 页面内执行：DOM 查询、事件派发、canvas 抓图  │
└────────────────────────┬───────────────────────────────────────┘
                         │  真实 DOM 事件 / canvas 导出
┌─ 第 4 层：页面 ────────▼───────────────────────────────────────┐
│  zhipin.com：DOM 列表、会话面板、WASM canvas 在线简历           │
└───────────────────────────────────────────────────────────────┘
```

### 各层职责边界

| 层 | 做 | 不做 |
| --- | --- | --- |
| CLI / MCP | 参数校验、编排流程、结果落盘 | 不直接接触页面 |
| 桥 | 路由、超时、连接生命周期、日志 | 不理解业务语义 |
| 扩展 | 页面操作原语（点击/输入/滚动/抓图/下载） | 不做评分、不做筛选决策 |
| 页面 | —— | —— |

**扩展刻意保持「哑」**：它只提供原子操作，所有判断逻辑在 CLI/MCP 侧。这样升级筛选规则不需要重载扩展。

## 4. 一次典型指令的数据流

以 `boss capture-resume <candidate-id>` 为例：

```
1. CLI 组装指令
   { id: "<req-id>", cmd: "captureResume", args: { candidateId: "<candidate-id>" } }

2. CLI → HTTP POST http://127.0.0.1:8898/cmd

3. 桥查连接表，挑一条健康 WS 连接，转发指令，登记 <req-id> 等待响应

4. 扩展 service worker 收到 → 转给目标标签页的 content script

5. content script 依次执行：
   a. 把窗口置前（windows.update focused + tabs.update active）
   b. 按会话 id 打开该候选人
   c. 轮询等面板指纹 == 目标（最长 20s）
   d. 打开在线简历 → 等待 canvas 渲染
   e. 分块导出 canvas（见 §6）
   f. 清理叠层弹窗

6. content script 回传结果 → SW → WS → 桥 → 按 <req-id> 唤醒 CLI

7. CLI 落盘：resume/<candidate-id>/chunk-*.png，并写索引 JSON
```

### 指令信封（示意）

```jsonc
// 请求
{ "id": "req-<n>", "cmd": "sendMessage", "args": { "candidateId": "<candidate-id>", "text": "..." }, "timeoutMs": 30000 }

// 响应（成功）
{ "id": "req-<n>", "ok": true, "data": { "verified": true, "evidence": ["inputCleared", "messageVisible"] } }

// 响应（失败）
{ "id": "req-<n>", "ok": false, "error": { "code": "FINGERPRINT_MISMATCH", "message": "面板指纹与目标不符" } }
```

> **设计原则**：写操作的成功必须带 `evidence`（可核验证据），不接受「已点击」这种弱确认。

## 5. MV3 service worker 保活

MV3 的 service worker 会在空闲约 30 秒后被浏览器回收。回收后 WS 连接断开，指令就没人处理了。

**做法**：扩展侧每 **15 秒**调用一次轻量平台信息读取（`getPlatformInfo`）作为心跳：

- 有定时活动 → SW 不被回收；
- 心跳同时把状态（当前标签页、是否已登录）报给桥；
- 桥侧据此维护「连接是否新鲜」，超过阈值未收到心跳即标记为**疑似僵尸**。

**桥还需要主动清理僵尸连接**：WebSocket 的 `close` 事件在网络异常时可能不触发，连接会留在表里，导致指令被**死连接吃掉**（表现为「指令发出去了但一直不返回」）。所以桥在转发前会跳过心跳过期的连接，并定期剪除。

## 6. 为什么要分块传输大响应

**实测边界**：单次响应约 **40KB 正常**，**超过约 55KB 就不返回**，且卡住之后**其它指令仍然秒回**——这说明卡的是**响应通道**（单条消息体过大），不是页面卡死。

在线简历 canvas 是长图（可达数千像素高），全量 PNG 明显超出上限。

**做法：分块抓取**

```
把 canvas 切成 2×2 四块
每块按原生分辨率导出（约 50KB/块）
逐块返回 → 桥按序转发 → CLI 侧拼接成完整长图
```

**注意点**：

- canvas 的**内部像素尺寸**与 **CSS 显示尺寸**可能不同，抓图要用内部尺寸，否则会模糊；
- 分块必须**按序**拼接，CLI 侧用块索引重组；
- 后续若简历更长，可扩展为 N×M 分块，但**单块体积必须留在安全区内**。

## 7. 扩展改动后必须重载

MV3 有**多层缓存**，改了 `content.js` 不重载会继续跑旧代码：

| 缓存层 | 清法 |
| --- | --- |
| Service Worker 实例 | `chrome://extensions` → 扩展卡片的「Service Worker」→ 点「终止」 |
| Extension State | 点卡片上的「刷新 / Reload」 |
| Code Cache（磁盘字节码缓存） | `chrome://settings/clearBrowserData` → 只勾「缓存的图片和文件」 |
| 已注入的 content script | 必须**重新加载目标页面**（旧注入的脚本不会自动更新） |

**推荐动作序列**：

```
改代码 → chrome://extensions 点「刷新」→ 关闭 Boss 标签页 → 清 Code Cache（可选）→ 重开页面
```

> 清 Code Cache **不影响登录态**；清 cookie 才会。详见 [INSTALL.md §9](INSTALL.md#9-升级)。

## 8. 安全与隐私边界

| 事项 | 设计 |
| --- | --- |
| 监听地址 | 桥只绑 `127.0.0.1`，不监听 `0.0.0.0`，局域网不可达 |
| 出网 | 桥与 CLI **不向任何第三方服务器发送数据** |
| 扩展权限 | 只申请 `zhipin.com` 域 + 必需的最小 API，见 [INSTALL.md §2](INSTALL.md#扩展需要的最小权限) |
| 候选人数据 | 全部落本地磁盘，不加密上传、不遥测 |
| 凭据 | 登录态保存在**专用 profile 目录**，不进仓库、不进日志 |
| 日志 | 指令日志**只记 id 与命令名**，不记消息正文、不记简历内容 |

> **本地桥没有鉴权**：任何能在你机器上发 HTTP 请求的进程都可以驱动它。请确保本机环境可信；不要在多用户共享机器上长期运行。
