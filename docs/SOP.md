# 招聘初筛作业 SOP

> 本文解决什么问题：把「我该按什么口径筛人、怎么打分、怎么触达、最后交什么」一次性定死，让筛选结果**可复现、可解释、可被 HR 采信**。

**适用范围**：你账号内某个在招岗位的候选人初筛。**所有阈值都是默认值**，请按自己岗位调整；调整后**必须写进人才画像文档**，让口径可追溯。

---

## 0. 总览：两段式筛选

```
第一段：列表级硬门槛（G1–G6）
  ↓ 不开简历，只看列表字段
  ↓ 产出：通过 / 淘汰 + 淘汰原因
  ↓ 目的：把池子从几百人砍到几十人，省掉开简历的成本

第二段：在线简历精筛（八维度 100 分）
  ↓ 只对第一段通过的人开简历
  ↓ 产出：分数 + 分级 + 每维度原文证据
  ↓ 目的：给出「谁值得约面」的可解释排序

第三段：触达与收集（不是筛选，是转化）
  ↓ 开场话术 → 求简历 → 收藏 → 收简历 → 致谢
```

**为什么分两段**：开在线简历是**最贵**的操作（要置前窗口、等渲染、分块抓图），也是**最容易被限流**的操作。先用列表字段砍掉大部分不匹配的人，能显著降低风险。

---

## 1. 第一段：列表级硬门槛（G1–G6）

### 1.1 字段来源

全部来自**列表页/会话面板**，**不需要打开在线简历**：

| 字段 | 说明 |
| --- | --- |
| 年龄 | |
| 学历 | |
| 工作年限 | |
| 当前公司及岗位 | |
| 期望城市 / 期望薪资 | |
| **打招呼留言全文** | **多轮的都要**（候选人常分几条发，只读最后一条会漏信息） |

```bash
boss list --limit 200 --json > ./_过程文件/list.json
```

### 1.2 门槛定义

| 编号 | 门槛 | 判定 | 不通过处理 |
| --- | --- | --- | --- |
| **G1** | 学历 | **本科及以上** | 大专：**扣 5 分后仍可入池**（见 §2.4 否定项）；大专以下：淘汰 |
| **G2** | 工作年限 | **≥ 1 年正式经验** | 淘汰（实习/在校不计入） |
| **G3** | 地域 | **大湾区**，**深圳优先** | 非大湾区：淘汰；大湾区非深圳：入池但降序 |
| **G4** | 期望薪资 | 期望**上限 ≤ 16K** | 超预算：淘汰（留言里已说明可谈的，进人工复核） |
| **G5** | 岗位方向 | **开发岗**（与在招方向一致） | 非开发岗：淘汰 |
| **G6** | 到岗 | **可到岗**（非明确「暂不考虑机会」） | 明确不考虑：淘汰 |

> **注意 G4/G6 的例外**：候选人在打招呼留言里主动说明「薪资可谈」「随时到岗」的，以**留言为准**，进人工复核队列，不要机械淘汰。

### 1.3 产出格式

每个人一条记录，**淘汰必须给出原因且原因要能复述**：

```jsonc
{
  "candidateId": "<candidate-id>",
  "stage1": {
    "pass": false,
    "failedGates": ["G4"],
    "reason": "期望上限 20K，超出岗位预算 16K",
    "evidence": ["打招呼留言原文：「期望 18–20K」"]   // 必须附原文
  }
}
```

```bash
# 1) 取列表（务必保留打招呼留言全文）
boss list --limit 200 --json > ./_过程文件/list.json

# 2) G1–G6 判定：由你（或 Agent 按 skills/boss-recruiting）按上表执行，
#    结果写入 ./_过程文件/stage1.json
#    本仓库 CLI 不内置评分命令：筛选口径与命令解耦，便于按岗位改规则而不用改代码
```

> **原则**：G1–G6 是**硬门槛**，不做「综合感觉还不错所以放进来」——那是第二段的事。

## 2. 第二段：在线简历精筛（八维度 100 分）

只对**第一段通过**的候选人执行。每人流程见 [examples/runbook-初筛.md](../examples/runbook-初筛.md)。

### 2.1 维度与权重

| 维度 | 名称 | 满分 | 看什么 |
| --- | --- | --- | --- |
| **D1** | 独立闭环交付 | **25** | 能否独立把一件事从头做到尾：需求 → 设计 → 开发 → 上线 → 维护。看有没有「一个人负责过一个系统/模块」的经历描述 |
| **D2** | 业务理解与需求拆解 | **20** | 是否理解业务目标、能否把模糊需求拆成可执行任务；简历里有没有讲清「为什么做」而不只是「用了什么」 |
| **D3** | 技术栈重合度 | **15** | 与岗位要求技术栈的匹配程度 |
| **D4** | 稳定性与性价比 | **15** | 每段经历时长、跳槽节奏、期望薪资与能力是否匹配 |
| **D5** | 工程化交付 | **12** | 版本管理、测试、CI/CD、代码规范、发布流程、监控排障等工程习惯 |
| **D6** | 接手维护旧系统 | **5** | 有无接手他人遗留系统并稳定运行/逐步改造的经历 |
| **D7** | ERP / 低代码 / 二开 | **4** | ERP、低代码平台、二次开发相关经验 |
| **D8** | AI 辅助编码实操 | **4** | **实际用 AI 工具提效的痕迹**（见 §2.3） |

**合计 100 分。**

### 2.2 评分档位建议

每个维度不要「感觉给分」，按语义档位打分再取整：

| 档位 | 建议比例 | 语义 |
| --- | --- | --- |
| 优秀 | 满分 × 0.85–1.0 | 有明确、具体、可验证的经历支撑 |
| 良好 | 满分 × 0.65–0.85 | 有相关经历，但细节或深度不足 |
| 一般 | 满分 × 0.4–0.65 | 只提到概念，缺少实际成果 |
| 弱 | 满分 × 0.15–0.4 | 只有零散提及 |
| 无证据 | **0** | **没有任何原文可引 → 强制 0 分** |

### 2.3 关于 AI / RAG / Agent（重要）

> **AI / RAG / Agent 本身不作为加分项。**

- 简历里写「做过 RAG 知识库」「做过 Agent 工作流」**不加分**；
- 只有 **D8** 认可「**用 AI 工具提升编码效率**」的**实操痕迹**（例如：说明用 AI 做了哪些具体环节、效率变化、如何校验 AI 产出）；
- 判断方向性能力的仍然只有 **D1/D2**：**看业务系统交付能力**，不看技术名词热度。

**这么做是因为**：AI 相关名词极易包装、无法在初筛阶段证伪；而「独立交付过业务系统」是能通过简历细节交叉验证的。

### 2.4 否定项（在八维度得分基础上扣）

| 否定项 | 扣分 | 判定要点 |
| --- | --- | --- |
| 纯算法，无业务系统经验 | **−15** | 全部经历都是模型/算法研究，无工程交付 |
| 仅大厂细分模块 | **−10** | 只做过大厂某个很窄的模块，缺少端到端视野 |
| 近两段经历每段 **< 1 年** | **−15** | 「近两段」指最近两段正式经历 |
| 履历矛盾 | **−20** | **时间线对不上、年限与经历不符、公司/岗位前后冲突** |
| 大专 | **−5** | 与 G1 呼应：大专扣分后可入池 |

**履历矛盾的处理**：一旦发现，**不要自行猜测**，在报告里标注矛盾点并附两处原文，交人工判断。

### 2.5 总分与分级

```
总分 = Σ(D1..D8) − Σ(否定项)，下限 0

S ≥ 70   强烈推荐，优先约面
A 55–69  推荐，进备选前列
B 40–54  观望，视岗位缺口决定
C 25–39  暂不推进，留档
D < 25   淘汰
```

```bash
# 八维度打分：由你/Agent 读图后按 §2.1–§2.5 写分，
# 每个维度都必须带候选人原文摘录 → 落 ./_过程文件/scores.json

# 逐人核验：指纹 + 话术 + 求简历 + 收藏（这是本仓库内置的核验命令）
boss audit --people ./_过程文件/people.json --json
```

### 2.6 证据要求（硬规则）

> **每个维度都必须附候选人原文摘录。没有摘录的维度按 0 分。**

- 摘录必须**逐字来自**候选人简历或打招呼留言，**不允许改写、不允许总结后当摘录**；
- 摘录要能**定位**（第几屏 / 哪一段 / 哪个模块）；
- 一条摘录**只能支撑一个维度**的主要判断，跨维度复用要说明理由；
- 报告输出时，评分表与摘录**放在一起**，方便 HR 复核。

**记录格式**：

```jsonc
{
  "dimension": "D1",
  "score": 21,
  "max": 25,
  "evidence": [
    {
      "source": "在线简历 · 工作经历 · 第 2 段",
      "quote": "<候选人原文逐字摘录>"
    }
  ],
  "rationale": "独立负责过完整系统的需求到上线"
}
```

## 3. 触达与收集

> 顺序很重要：**先开场 → 再求简历 → 顺带收藏 → 收到后致谢**。

### 3.1 开场话术

**结构**：一句话认可 + 只提一个请求（要一份 PDF 简历）。

```
您好，看到您在 <方向> 方面的经历，和我们 <岗位> 比较匹配。
方便发一份 PDF 简历吗？我这边可以同步看下细节。
```

**规则**：

| 要做 | 不要做 |
| --- | --- |
| 只提「方便发一份 PDF 简历吗」 | **不要问到岗时间**（留到约面阶段） |
| 异地/超预算时才顺嘴说明一句 | 不要一上来就压薪资 |
| 保持一句话能读完 | 不要发长段落、不要加多余链接 |

> **不要问到岗时间**是有意为之：初筛阶段的到岗时间信息价值低，但会显著提高候选人警觉与流失率。

```bash
boss send <candidate-id> --text "<开场话术>"
```

**核验**：输入框清空 **且** 会话里出现该消息。

### 3.2 求简历（两步）

```bash
boss request-resume <candidate-id>
```

1. 点工具栏 `求简历`；
2. 确认框「确定向牛人索取简历吗？」→ 点 `确定`；
3. **核验**：会话里出现系统消息「**简历请求已发送**」。

### 3.3 收藏

```bash
boss favorite <candidate-id>
```

> **先读当前收藏状态再点**，否则会把「已收藏」点成「取消收藏」。工具内部已做幂等，自己写脚本时要格外注意。

### 3.4 收简历（附件简历下载）

```bash
boss download-resume <candidate-id> --out-name <序号>_<姓名>.pdf
```

流程见 [PITFALLS.md D3](PITFALLS.md#d3-附件简历下载)：点附件简历 → 从预览 iframe 的 `url` 参数解出真实地址 → 下载 → **校验 `%PDF` 文件头**。

命名约定：

```
<序号>_<姓名>.pdf        # 序号为评分排名，便于按顺序翻阅
```

**重名处理**：文件名冲突时**不要覆盖**，追加会话 id 后 6 位（如 `<序号>_<姓名>_<id6>.pdf`）。

### 3.5 致谢

收到简历后回一条标准致谢：

```
简历已收到，感谢！我这边看完会尽快同步下一步安排。
```

```bash
boss send <candidate-id> --text "<致谢话术>"
```

### 3.6 触达节奏

| 参数 | 默认值 |
| --- | --- |
| 单人操作间隔 | **15–20 秒** |
| 连续工作时长 | **40–60 分钟**，之后冷却 **30–60 分钟** |

详见 [OPERATIONS.md §4](OPERATIONS.md#4-节奏控制)。

## 4. 交付物契约

**每次固定产出以下四项**，不多不少。

```
输出/
├── 最终筛选名单_<岗位>.xlsx        ← 名单 + 维度得分 + 评分口径 + 跟踪列
├── 人才画像与筛选标准_<岗位>.docx   ← 唯一一份文字材料
├── 在线简历汇编报告.pdf             ← 每人 1 页评分摘要 + 在线简历逐屏截图
└── 简历PDF/                        ← 收到的附件简历（<序号>_<姓名>.pdf）
```

> 过程产物（列表 JSON、分块截图、快照、日志）全部放 `_过程文件/`，**不进交付目录**。

### 4.1 最终筛选名单 xlsx

必须包含的列：

| 列 | 说明 |
| --- | --- |
| 序号 | 按总分降序 |
| 姓名 / 会话id | **会话 id 必填**，用于唯一标识 |
| 年龄 / 学历 / 年限 | 列表字段 |
| 当前公司 / 当前岗位 | 指纹字段 |
| 期望城市 / 期望薪资 | |
| D1…D8 各维度得分 | 8 列 |
| 否定项扣分 | |
| **总分 / 分级** | S/A/B/C/D |
| **评分口径** | 一行简述打分依据 |
| 已发送 / 已收藏 / 已收简历 / 已回复 | 4 个跟踪列（布尔或时间戳） |
| 备注 | 人工复核点（如履历矛盾） |

```bash
# 名单表由你/Agent 按上表列生成（xlsx）；产出落到 输出/
# 生成前先确认 输出/最终筛选名单_<岗位>.xlsx 没有被 Excel/WPS 打开
```

### 4.2 人才画像与筛选标准 docx

**唯一一份文字材料**，包含四部分：

1. **人才画像**：这个岗位真正想要什么样的人（不是 JD 的复述）；
2. **硬门槛**：G1–G6 的实际取值与例外说明；
3. **评分规则**：八维度定义、档位比例、否定项、阈值（即本文 §2 的可读版）；
4. **面试验证清单**：初筛里**无法证伪**、必须留到面试核实的点（如独立闭环的真实边界、履历矛盾的澄清）。

```bash
# 人才画像 docx 由你/Agent 按下面四部分撰写；产出落到 输出/
```

### 4.3 在线简历汇编报告 pdf

- **每人 1 页**；
- 内容：评分摘要（各维度得分 + 总分 + 分级）+ 该候选人的**在线简历逐屏截图**；
- 截图顺序与评分表顺序一致，便于对照。

```bash
# 汇编报告 pdf 由你/Agent 把"评分摘要 + 该人逐屏截图"逐人拼成 1 页；产出落到 输出/
```

### 4.4 简历PDF 目录

- 收到的**附件简历**原始文件；
- 命名 `<序号>_<姓名>.pdf`；
- 与名单里的序号一一对应。

### 4.5 交付前检查

```bash
boss audit --people ./_过程文件/people.json --json
```

检查项：

- [ ] 四项交付物齐全
- [ ] 交付目录无过程文件
- [ ] 每个候选人的每个维度都有原文证据
- [ ] 名单里的会话 id 与简历 PDF 一一对应
- [ ] 跟踪列状态与实际会话记录一致

## 5. 常见错误自查

| 自查项 | 错在哪 | 后果 |
| --- | --- | --- |
| 用姓名点列表行 | 没用会话 id | **可能发给重名的另一个人** |
| 打开后立刻读快照 | 没用轮询等指纹 | 读到上一个人的数据，评分全错 |
| 以为简历没加载 | 没检查窗口是否在前台 | 白等，或对着 300×150 空图评分 |
| 抓图超时 | 没分块 | 调用卡死 |
| 看到窄栏文字浮层 | 没清叠层 | 误判为页面异常，抓错内容 |
| 发送/求简历「成功」但没记录 | 用返回值而非会话消息核验 | 以为发了其实没发 |
| 某个维度没摘录却给了分 | 违反硬规则 | 报告不可信，HR 无法复核 |
| AI/RAG 经历加分 | 违反 §2.3 | 排序被名词热度带偏 |
